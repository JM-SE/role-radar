Job Search — Handoff técnico y funcional
1. Propósito de este documento
Este documento define el contexto, objetivos, arquitectura, alcance inicial, decisiones técnicas y plan de
implementación de una nueva aplicación llamada provisionalmente Job Search.
Debe utilizarse como handoff para iniciar el proyecto con un agente de desarrollo en OpenCode.
El objetivo no es generar todo el sistema en una sola iteración. El proyecto debe construirse
incrementalmente, con componentes pequeños, validaciones claras y una arquitectura preparada para
evolucionar sin introducir infraestructura innecesaria.

2. Contexto general
2.1 Problema que queremos resolver
Queremos construir una aplicación personal que busque oportunidades laborales de software
engineering, las normalice, elimine duplicados, descarte ofertas incompatibles y presente diariamente
las oportunidades más relevantes.
La herramienta debe reducir el trabajo manual necesario para:
• revisar múltiples portales de empleo;
• abrir ofertas irrelevantes;
• detectar restricciones geográficas;
• comparar tecnologías requeridas;
• reconocer empleos duplicados;
• identificar oportunidades compatibles con el perfil;
• priorizar las mejores postulaciones;
• mantener un registro histórico de lo encontrado.
La aplicación no debe limitarse a devolver enlaces obtenidos desde un buscador. Debe convertirse en
un pipeline persistente de adquisición, análisis, filtrado y ranking de oportunidades.

2.2 Referencia inicial
El punto de partida conceptual fue un workflow de n8n llamado Job Scrapper .
Ese workflow:
1. recibe o almacena un CV;
2. utiliza un modelo para convertirlo a una consulta de búsqueda;
3. ejecuta una única búsqueda mediante Tavily;
4. limita los resultados a dominios laborales;
5. toma hasta diez enlaces;

1

6. los envía mediante Telegram.
La idea de restringir la búsqueda a fuentes relevantes es útil, pero el workflow no realiza scraping real,
persistencia, deduplicación, extracción completa, matching profundo ni seguimiento histórico.
Este nuevo proyecto no debe copiar literalmente ese workflow. Debe conservar su simplicidad
conceptual y resolver sus limitaciones.

3. Infraestructura existente
3.1 Homelab
La aplicación será desplegada inicialmente en un homelab personal.
Características relevantes:
• Debian 13.
• CPU Ryzen 5 3600.
• 16 GB de RAM.
• GPU AMD RX 580 con 8 GB de VRAM.
• llama.cpp con backend Vulkan.
• Nginx como reverse proxy.
• Servicios administrados mediante systemd.
• Aplicaciones existentes basadas en FastAPI.
• YTPipe ya utiliza un modelo local para resumir videos de YouTube.

3.2 Modelos locales
Actualmente se utiliza:

Qwen3-4B-Instruct-2507-Q4_K_M
Este modelo se utiliza para tareas rápidas y estructuradas, especialmente dentro de YTPipe.
Se incorporará también:

Qwen3-4B-Thinking-2507-Q4_K_M
La estrategia definida es mantener dos modelos especializados, pero cargar solamente uno a la vez.

Modelo Instruct
Responsabilidades:
• YTPipe.
• Extracción estructurada de ofertas.

2

• Clasificación de ofertas.
• Normalización de campos.
• Resúmenes cortos.
• Identificación de requisitos y evidencia.
• Tareas que no necesitan razonamiento extenso.

Modelo Thinking
Responsabilidades:
• Evaluación profunda de ofertas finalistas.
• Análisis de compatibilidad entre experiencia y requisitos.
• Interpretación de requisitos ambiguos.
• Identificación de fortalezas, brechas y riesgos.
• Recomendación final de postulación.
• Revisión de casos con información contradictoria.
Inicialmente no se utilizará un modelo de 8B.
Un modelo mayor solamente será considerado si una evaluación controlada demuestra que el modelo
Thinking de 4B falla significativamente en el ranking o en la interpretación de casos relevantes.

4. LLM Broker
4.1 Estado actual
Ya se inició otro proyecto independiente llamado provisionalmente LLM Broker.
Está siendo desarrollado en Go como ejercicio de aprendizaje y como componente reutilizable de
infraestructura.
El broker debe ser agnóstico respecto de las aplicaciones consumidoras y los modelos concretos.
Sus responsabilidades incluyen:
• encolado de solicitudes;
• priorización;
• selección de modelo;
• model swapping;
• coordinación de workloads;
• control de concurrencia;
• interacción con llama.cpp o llama-swap;
• exposición de estado;
• prevención de cambios perjudiciales de modelo;
• aislamiento entre aplicaciones consumidoras.

4.2 Relación entre Job Search y el broker
Job Search no debe:
• iniciar llama-server;
• detener llama-server;
• reiniciar servicios de modelos;
• administrar directamente llama-swap;
• decidir cómo cargar modelos;
• conocer rutas locales de archivos GGUF;
• asumir qué modelo está cargado;
• implementar su propia cola de inferencia global.
Job Search debe consumir el LLM Broker como un servicio externo.
La aplicación podrá solicitar capacidades conceptuales como:

structured-extraction
deep-job-evaluation
short-summary
Idealmente, Job Search no debería depender directamente del nombre físico del modelo.
El broker decidirá qué modelo satisface cada capacidad.

"priority": "normal",

"prompt": "...",
"response_schema": {}
}
}
Para evaluación profunda:

5.3 Motivos para utilizar Python
Job Search será principalmente una aplicación de:
• ingestión de datos;
• parsing de HTML;
• normalización de texto;
• extracción estructurada;
• experimentación con prompts;
• evaluación de modelos;
• procesamiento batch;
• cálculo de métricas;
• análisis de datasets.
Python ofrece un ecosistema especialmente apropiado para estas tareas.
La división tecnológica queda conceptualmente así:

LLM Broker → Go
Job Search → Python
YTPipe → consumidor existente
Frontend futuro → React o React Native

5.4 Alternativas descartadas inicialmente
Go
Sería viable, pero ya se está utilizando en el broker. Python ofrece mayor velocidad de experimentación
para extracción, scoring y evaluación de modelos.

TypeScript y NestJS
Sería una alternativa válida, pero aporta menos valor para procesamiento de datos y evaluación local de
LLMs.

Django
Podría ser útil si el proyecto necesitara inmediatamente un panel administrativo completo,
autenticación y múltiples usuarios. Para esta primera etapa introduciría demasiadas convenciones y
componentes.

Rust
No se justifica para una aplicación experimental cuyo dominio todavía cambiará frecuentemente.

6. Principios arquitectónicos
6.1 API, worker y scheduler separados
FastAPI será la interfaz HTTP, pero no ejecutará directamente el batch completo.
La aplicación tendrá tres procesos conceptuales:

API
Worker
Scheduler

API
Responsabilidades:
• consultar ofertas;
• consultar ejecuciones;
• administrar el perfil;
• cambiar estados;
• registrar feedback;
• iniciar una ejecución manual;
• exponer salud y métricas básicas.

Worker
Responsabilidades:
• recolectar ofertas;
• normalizar resultados;
• deduplicar;
• ejecutar extracción;
• calcular scores;
• solicitar evaluaciones al broker;
• persistir resultados;
• preparar notificaciones.

Scheduler
Responsabilidad:
• crear ejecuciones programadas.
Inicialmente se recomienda utilizar un systemd timer que invoque un comando CLI de la aplicación.
Ejemplo conceptual:

7

job-search run create --reason scheduled
No se utilizará FastAPI BackgroundTasks para ejecutar el pipeline completo.

6.2 Procesamiento persistente
Una ejecución no debe depender de mantener abierta una petición HTTP.
La API debe poder responder:

{
"run_id": "run_123",
"status": "pending"
}
Luego el worker procesa la ejecución independientemente.
Si el worker o la API se reinician, la ejecución debe poder continuar o reintentarse.

6.3 Una sola máquina y un solo worker inicialmente
No se necesita una arquitectura distribuida.
Primera versión:
• un único servidor;
• un único worker;
• una única base SQLite;
• un único scheduler;
• broker externo para inferencia.
No introducir inicialmente:
• Celery;
• Redis;
• Kafka;
• RabbitMQ;
• Kubernetes;
• múltiples workers;
• locking distribuido.

8.2 Datos personales
Nombre, teléfono, email y otra información sensible no son necesarios para evaluar una oferta.
El matching debe trabajar con un perfil profesional reducido.
El CV completo solo será necesario más adelante para:
• adaptar una postulación;
• redactar una presentación;
• preparar una respuesta;
• generar una versión específica del CV.
Estas funciones no forman parte del MVP.

9.2 Fuentes prioritarias
Orden inicial recomendado:
1. Greenhouse.
2. Lever.
3. Ashby.
4. Workable.
5. Búsqueda web mediante proveedor configurable.
6. Páginas genéricas de empresas.
7. Alertas de LinkedIn por correo.

9.3 ATS estructurados
Cuando un ATS entrega campos estructurados, esos campos deben considerarse preferibles al
resultado del LLM.
Ejemplos:
• título;
• empresa;
• ubicación;
• ID externo;
• URL de aplicación;
• departamento;
• fecha de publicación.
El LLM no debe redescubrir información que la fuente ya proporciona correctamente.
Debe utilizarse para extraer información que permanece dentro de la descripción:
• requisitos;
• skills obligatorias;
• skills deseables;
• autorización laboral;
• idiomas;
• modalidad contractual;
• salario si aparece en texto;
• restricciones regionales;
• años de experiencia.

9.4 Búsqueda web
La búsqueda web será una fuente de descubrimiento, no una fuente de verdad.
Debe existir una abstracción:

class SearchProvider(Protocol):
async def search(self, query: SearchQuery) -> list[SearchResult]:
...
Tavily puede ser una implementación inicial, pero no debe estar acoplado al dominio.
Las búsquedas deben poder restringirse a portales como:
• Greenhouse;
• Lever;
• Ashby;
• Workable;
• Wellfound;
• Work at a Startup;
• Workana;
• Get on Board;
• Revelo;
• LinkedIn.
No se debe generar una única consulta demasiado restrictiva.
Debe existir un conjunto controlado de consultas por:
• rol;
• título;
• stack;
• región;
• modalidad contractual.

9.5 LinkedIn
No se debe implementar scraping autenticado de LinkedIn.
Queda explícitamente fuera del alcance:
• utilizar credenciales del usuario;
• automatizar login;
• conservar cookies;
• utilizar Playwright con una sesión personal;
• eludir CAPTCHA;
• simular comportamiento humano;
• hacer crawling de resultados autenticados.
Las vías aceptables son:

Descubrimiento mediante buscadores
Buscar páginas públicas indexadas del dominio LinkedIn.
Ejemplo conceptual:

Alertas oficiales por correo

debe preferirse la fuente original.

10.2 Recolección
Los collectors configurados obtienen ofertas.
Cada resultado se persiste inicialmente como RawJob .
Debe conservarse suficiente información para poder reproducir o depurar el procesamiento.

10.3 Normalización
La normalización incluye:
• limpieza de URLs;
• eliminación de parámetros de tracking;
• normalización de nombres de empresa;
• normalización de espacios;
• conversión de HTML a texto;
• detección de IDs externos;
• normalización de ubicaciones;
• normalización básica de títulos.

10.4 Deduplicación
La deduplicación debe utilizar varias señales, en orden:
1. fuente + ID externo;
2. URL de aplicación normalizada;
3. URL de fuente normalizada;
4. empresa + título + ubicación;
5. fingerprint de empresa, título y descripción.
Una misma oferta puede aparecer mediante:
• LinkedIn;
• Tavily;
• página de careers;
• ATS;
• email.
Debe mantenerse una entidad canónica y varias referencias de origen.

10.5 Prefiltros determinísticos
Antes de usar el modelo pueden descartarse casos evidentes:
• rol completamente ajeno;

16

• ubicación presencial incompatible;
• oferta eliminada;
• URL inválida;
• contenido vacío;
• duplicado ya procesado;
• país explícitamente incompatible;
• tecnología central expresamente excluida.
Los prefiltros deben ser conservadores.
Es preferible mantener temporalmente una oferta dudosa que eliminar una oportunidad valiosa
demasiado pronto.

10.9 Selección para Thinking
No todas las ofertas deben pasar por el modelo Thinking.
Candidatos posibles:
• score preliminar alto;
• oferta interesante con requisitos ambiguos;
• conflicto entre reglas;
• región poco clara;
• seniority ambiguo;
• skill principal transferible pero no exacta;
• puesto con buen encaje general y un posible bloqueo;
• ofertas cercanas al umbral de decisión.
Los thresholds deben ser configurables.
Ejemplo inicial:

score >= 75 → deep evaluation
55–74 con ambigüedades → deep evaluation
score < 55 sin señales especiales → no deep evaluation
hard blocker seguro → no deep evaluation

10.10 Procesamiento agrupado por modelo
El orden debe evitar alternar modelos por cada oferta.
Secuencia:
1. recolectar todas las ofertas;
2. normalizar;
3. deduplicar;
4. aplicar filtros;
5. procesar todas las extracciones con Instruct;
6. persistir todos los JSON;
7. calcular todos los scores preliminares;
8. construir la cola de evaluación profunda;
9. solicitar Thinking para toda esa cola;
10. volver a dejar disponible Instruct.
El LLM Broker debe coordinar este comportamiento.
Job Search no debe implementar el swap directamente.

Thinking recibe solamente:
• perfil profesional normalizado;
• extracción estructurada;
• evidencia relevante;
• score preliminar;

• ambigüedades;
• preguntas concretas.
No debe recibir nuevamente toda la página HTML.

Valores sugeridos:

- strong_match

- apply

10.12 Regla final
El modelo nunca puede ignorar un hard blocker confirmado por código.
Ejemplos:
• requiere residencia en Estados Unidos;
• requiere autorización laboral no disponible;
• es presencial en una región incompatible;
• no acepta candidatos desde Argentina;
• exige una tecnología central excluyente;
• modalidad incompatible definida como restricción dura.
Se recomienda mantener:

preliminary_score
thinking_score
thinking_adjustment
final_score
El ajuste del modelo puede limitarse inicialmente a un rango, por ejemplo:

-15 a +15
El score final siempre debe ser calculado por código.

15. Prompts y versionado
Los prompts no deben estar dispersos como strings arbitrarios dentro de servicios.
Deben:
• almacenarse en archivos dedicados;
• tener una versión;
• incluir el schema esperado;
• ser testeables;
• registrar qué versión produjo cada resultado.
Ejemplo:

prompts/
├── job_extraction_v1.md
├── job_extraction_repair_v1.md
└── deep_match_v1.md
Cada resultado persistido debe guardar:

prompt_version
schema_version
model_identifier
Esto permitirá comparar resultados después de modificar un prompt.

16. Evaluación de calidad
Antes de confiar en el ranking, se debe preparar un dataset manual de entre 50 y 100 ofertas.
Cada oferta debe tener etiquetas humanas como:

29

interesting
not_interesting
hard_blocker
possible_match
strong_match
También deben señalarse:
• restricciones geográficas;
• modalidad;
• skills principales;
• requisitos ambiguos;
• decisión recomendada.

Métricas prioritarias
Hard-blocker recall
De todas las ofertas imposibles:

¿Cuántas fueron bloqueadas correctamente?

Interesting-job recall
De todas las ofertas interesantes:

¿Cuántas sobrevivieron al pipeline?

Top-10 precision
De las diez primeras:

¿Cuántas realmente merecían atención?

Ranking stability
Ejecutando varias veces la misma entrada:

¿Cuánto cambia el orden?

Extracción estructurada
Medir:
• exactitud de ubicación;

30

• exactitud de modalidad;
• exactitud de skills;
• exactitud de autorización laboral;
• porcentaje de JSON válido;
• porcentaje de reintentos;
• evidencia incorrecta o inventada.

Valor marginal de Thinking
Comparar:

Reglas solamente
Reglas + Instruct
Reglas + Thinking
Reglas + modelo mayor, solo si se prueba
La pregunta decisiva es:

¿Cuántas veces Thinking mejora correctamente una decisión?
No debe incorporarse un modelo de 8B sin demostrar una mejora significativa.
